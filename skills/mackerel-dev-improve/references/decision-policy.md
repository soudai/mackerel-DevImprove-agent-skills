# 改善の判定ポリシー

指標は「どこを調べ、どの改善を先にするか」の根拠。未知のバグ数、個人の能力、単一の品質点数に変換しない。観測された不具合と潜在的な変更リスクを分ける。

## 優先する判断

| 観測 | 最初の対応 |
|---|---|
| 最新runが不完全、shard欠落、CCCCのparse error・読取漏れ | 計測経路・解析対象を確認。品質改善と判定しない |
| テスト失敗・error、再現できるバグ | 失敗を再現し、仕様と原因を特定。複雑度の低さを免罪符にしない |
| pass率上昇と同時にselected/executed減少、skip増加 | 選択条件、削除、隔離、早期終了を確認 |
| retry後だけpass、flaky増加 | 状態共有・競合・外部依存・時刻依存を調査。再試行回数増加を修正としない |
| coverageやmutationが低い | 境界値・重要な振る舞い・assertionを強化。書きづらさに構造原因があれば責務を分ける |
| 高複雑度と高churn・不具合・変更予定が重なる | 対象を限定し、回帰テスト後に構造改善 |
| 低複雑度でも不具合が反復 | 認可、仕様、SQL条件、状態遷移、並行性を調査 |
| latency低下とthroughput低下 / dropped負荷増加 | 性能改善と判定しない。送信できた負荷を確認 |

## 閾値はプロファイル別に校正する

初期運用では2〜4週間、または代表的な変更・負荷が揃うまで観測し、実際の負担と一致する条件を選ぶ。これは提案値であり必須の待機期間ではない。既存の妥当な品質ゲートがあれば引き継ぐ。

| 指標 | 調査開始の例 | 扱い |
|---|---|---|
| 関数の循環的複雑度 | `> 10` | 解析器の分岐カウントに依存。moznion/ccccのcyclomaticへ採用する際も校正する |
| 認知複雑度 | `> 15` | 多くのSonar言語の参考値。C/C++/Objective-Cの既定25を含め、言語別に判断 |
| NPath | `> 200` | 対応する追加解析器のみ。CCCCのcognitive/cyclomaticから推定しない |
| CRAP | `> 30` | テスト不足を含む変更リスク候補。構造の改善を別に確認 |
| 新規重複 | `> 0.03` | 採用する場合の提案。業務ルールの重複かを確認 |
| 禁止依存 | 新規違反 `> 0` | 明示したアーキテクチャルールに限る |
| 変更の集中 | 90日の変更PR数が同じ層の上位20% | 少数母集団では順位に頼らず明細を見る |

表の15/10/200/30等は一律の合否基準にしない。`>` と `>=`、比較対象、例外条件を設定に記録する。認知複雑度15は経験的な調整値で、C系には別の既定値がある。[Sonar開発者の説明](https://community.sonarsource.com/t/s3776-reason-for-the-current-default-value-of-15/127103)。PHPMDの循環・NPathの設定値も、他解析器の規格値として流用しない。[PHPMD Code Size](https://phpmd.org/rules/codesize.html)

## 新しい問題と既存の問題

PRでは、新規の妥当な解析エラー・禁止依存を増やさず、変更する重要な振る舞いのテストを確保する。新規関数の超過、既存超過関数の悪化は、局所修正か理由付き例外として扱う。既存の負債があるだけで無関係な変更を全停止しない。

既存コードは次の条件で候補にする。

```text
構造上の警告 = 複雑度超過 OR 禁止依存 OR 循環依存
改善の必要性 = 変更集中 OR 近い変更予定 OR 関連する反復不具合
優先候補 = 構造上の警告 AND 改善の必要性
```

直近90日の追加行+削除行、変更PR数、同時変更module数を使う。生成コード・整形・機械置換・mergeの二重計数を分け、renameを追跡する。PR情報がなければcommit頻度として明示し、PR数に見せない。欠陥とchurnの関連は優先順位の仮説であり、因果の証明ではない。[Microsoft Research](https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/)

候補ごとに対象、根拠、影響、前提テスト、期待効果を成果物へ記録する。外部Issue登録・担当者への連絡・期限の設定は依頼範囲に含まれる場合に行う。例外には理由、見直し条件、設定済みの担当者や期限を残し、baseline更新だけで警告を隠さない。

## 効果検証

- バグ修正は修正前に失敗し修正後に成功する再現テストで確認する。ログのerror消失だけで解決としない。
- リファクタリングは対象挙動、回帰テスト、変更箇所の複雑度、結合度・重複の変化を評価する。
- 性能改善は同じデータ・リクエスト構成・資源制限・warmup・負荷・計装設定で反復する。可能ならbase/headを交互に測る。標本数・ばらつき・要求を送れなかった件数も報告する。
- 合格幅は基準のばらつきと要求から先に決める。1回のp95低下やテスト数の増加だけで成功としない。開発環境の結果を本番SLO達成とは表現しない。
- coverageだけでCRAPが下がった場合は「テスト保護を改善」とし、「構造を改善」と分ける。カバレッジは実行範囲でありassertionの正しさを保証しない。

例: moznion/ccccのcognitive=28、cyclomatic=18、90日変更PR=14、分岐coverage=0.45なら、対応関数の重要な分岐をテストで保護してから責務を整理する。cyclomatic=4でも同じ領域に回帰不具合が反復するなら、複雑度削減より原因調査を優先する。例は説明用の架空値。

報告する比較表: `対象 / base / head / 分母・対象数 / 差分 / 比較可能性 / 判定 / 根拠URI`。全体平均に加えて変更対象を表示する。
