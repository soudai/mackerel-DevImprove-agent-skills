# プロジェクトへの導入

導入先の実行方法と出力を確認し、対応するアダプターから使う。言語が同じでもランナーの版・レポート形式・再試行設定が異なれば、同じ意味で集計できるとは限らない。同梱CLIの対応範囲は [report-tools.md](report-tools.md) を正本とする。

## 最初に確定する対応表

既存設定から次の情報を取り、未確認の項目だけを補う。複数サービスを持つリポジトリではサービスごとに記録する。

| 対象 | 確認する情報 |
|---|---|
| サービスと環境 | componentのルート、OTelのservice属性、開発環境、Mackerel service名の対応 |
| 実行 | 既存コマンド、作業ディレクトリ、必要なruntime、実行版、CIのjob・shard・retry構成 |
| 計測 | レポートの生成元・形式・保存先、対象の選択・除外、完全な実行と中断を識別する証拠 |
| 既存の観測 | SDK・Collector・ログ形式、trace context伝播、データ量・sampling・利用可能な接続経路 |
| 成果物と投稿 | 保存先・閲覧権限・保持期間、基準ブランチ、投稿するCI、秘密情報の注入方法、単一writerの制御 |

対象環境にPythonや解析器を追加できるか、ネットワーク・proxy・コンテナ・実行時間の制約もここで確認する。既存の計装やCIを置き換える前に不足を特定する。依頼された開発環境の導入を、本番への送信や新たな定期実行へ自動的に広げない。

## 固定profileの分け方

- monorepoでは、独立したサービスを別bundle・Mackerel serviceへ対応させる。同一サービス内のunit/integrationや言語別静的解析は、少数の固定profileとして分けられる。
- profileは比較する母集団と計測定義の単位にする。異なるsuite、解析言語、runtime条件、rulesetを混ぜる必要がなければ分離し、対応表に残す。
- 測定条件は対応するCLI設定や `ruleset_hash` などへ反映し、単なる説明文で済ませない。定義変更で比較キーが変わる場合、同梱publisherは同名profileへの投稿を拒否する。別の固定profile名で新しい基準を取得し、別定義の値を同じ履歴上の改善として扱わない。
- PR番号、個人名、run ID、commit IDからprofileを生成しない。PRの結果はrunごとの成果物へ保存し、共有系列への投稿は指定した基準ブランチの経路へ集約する。

## レポートと共通処理の境界

```text
ランナーの生レポート + 実行証拠
  ├─ 対応済みの生成元 → 同梱アダプター
  └─ 別の生成元 → 生成元別converter → 共通tests JSON
                                       ↓
                              正規化bundle → publisher
```

別の生成元には [共通tests JSON](portable-tests.md) を使う。converterは生成元のケースID、状態、完了判定を共通契約へ写す役割を持つ。publisherはランナーを実行したり、レポートの方言を推測したりしない。

共通JSONがあるだけで、すべてのランナー・retry・shard・coverageが対応済みになるわけではない。採用する生成元の実レポートで、成功、既知のテスト失敗、レポート欠落・中断を照合する。契約で表現できない意味や取得不能な値は、その対応範囲を明記して欠測として残す。未知のJUnitをPHPUnitとして指定し、検証を通過させない。

## CIへ接続する順序

1. 実行前にrevision、選択条件、独立した対象一覧、開始時刻を記録する。CCCCの対象一覧は解析JSONから逆算しない。
2. 既存のテスト・解析コマンドを実行し、直後に元の終了コードを確保する。後続のcleanup、正規化、投稿の終了コードで上書きしない。複数jobや再試行の出力を区別して保存する。
3. テスト失敗後も、CIの `always` 相当の経路で取得できたレポートと実行証拠を保存する。job自体の中断などで収集できない場合は欠測とする。XMLが存在するだけで `test_plan_complete=true` にしない。
4. 新しい出力ディレクトリへ正規化し、オフラインの投稿検査を行う。正規化exit 0は測定の完全性であり、テスト合格ではない。CIの最終結果には元のテスト・品質ゲートの失敗を保持する。
5. 投稿用の資格情報は、信頼できる基準ブランチのpublisherだけに渡す。PR側の任意コマンドと投稿用資格情報を同居させない。成果物から転記した値だけでなく、CIの現在の公開対象とrevision/run/attemptを照合して、単一writerから投稿する。
6. メトリックとmetadataを読み戻し、ダッシュボードの単位・欠測・成果物リンクを確認する。具体的な送信条件と途中失敗の扱いは [投稿CLI](report-tools.md#mackerelへの投稿) に従う。

suiteごとのスナップショットを足してCI run数にしない。CI実行数が必要なら、同じrunを複数suite・shardで二重計数せず、run台帳から集計する。未対応の期間集計を既存CLIの出力に見せない。

## 導入完了の条件

実際の生成元・固定版から得た正常系と失敗系の結果を確認し、欠落した入力が成功や0件へ変換されないことを確認する。対象件数、完全性、元の終了コード、revision、測定時刻、成果物参照が一致してから比較に使う。

実送信を行った場合はAPI読戻しと表示まで確認する。通信・資格情報・対象環境が利用できない場合は、設定差分、生成したbundle、dry-run結果、残る確認項目を成果物にし、「導入済み」「可視化済み」とは区別して報告する。
